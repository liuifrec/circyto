# circyto v0.11.0: release and PyPI checklist

This procedure separates a **Git tag**, a **GitHub Release**, and **PyPI package publication**. They are different operations. The previously annotated `v0.10.0` tag remains at its June 2026 commit and **must not be moved or reused**. The November 2026 CMPB manuscript is *submitted*, not accepted or published; its historical analytical provenance is distinct from this newer software release.

## Release prerequisites

1. Review and merge the v0.11.0 release-preparation PR after both Python 3.10 and 3.12 CI jobs pass. Confirm `pyproject.toml`, `circyto/__init__.py`, `CITATION.cff` and `circyto --version` report **0.11.0**.
2. Confirm owner/institutional authorization for a **public software release**. The new Python distributions exclude CIRI3/CIRI-full Java binaries and the unlicensed CIRI-full manual; source archives generated by Git now use `.gitattributes` `export-ignore` for JAR/class/manual paths. This addresses a known redistribution exposure for new archives, **not** all historical repository content, all third-party permissions, or independent biological validation. Review [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md) and [distribution validation](detector_distribution_validation.md).
3. Record the exact verified main commit. Do not change that tree after creating the tag.

## A. Create an immutable new tag

From a clean local checkout with push access:

```bash
git fetch origin
git switch main
git pull --ff-only origin main
python -m pip install -e .
python -m pip check
circyto --version                     # must print 0.11.0
git status --short                      # should be empty
git tag -a v0.11.0 -m "circyto v0.11.0: native import, offline QC and distribution safeguards"
git push origin v0.11.0
```

Alternatively, use GitHub Releases > Draft a new release > Create new tag `v0.11.0` **from main**, then publish the GitHub Release with carefully scoped notes. Do not select or move `v0.10.0`. A GitHub Release alone does **not** upload to PyPI.

Before publishing, inspect an archive from the newly created tag; its source ZIP/tarball must contain **no `.jar`, `.class`, or `CIRI-full_manual.txt`**. The release workflow checks `git archive` automatically, while wheel/sdist members are checked independently. Historical archive downloads from older tags are unchanged.

## B. Configure PyPI Trusted Publishing once (owner action)

As of 26 November 2026, the public `https://pypi.org/project/circyto/` page returned 404, so do not assume the package exists or that the name is reserved.

1. Log in to PyPI as the intended package maintainer. For a new project, open [PyPI account publishing](https://pypi.org/manage/account/publishing/) and add a **pending GitHub trusted publisher** with exactly:
   - **PyPI project name:** `circyto`
   - **GitHub owner:** `liuifrec`
   - **Repository:** `circyto`
   - **Workflow filename:** `release.yml`
   - **GitHub environment name:** `pypi`
2. In GitHub, open repository Settings > Environments and create the `pypi` environment. Configure **required reviewers/manual approval** before publication, along with branch/tag restrictions appropriate to the release policy.
3. If `circyto` is registered on PyPI by someone else before the first publish, **stop** rather than upload under a name you do not control; a pending publisher does not reserve a name.
4. No password or long-lived PyPI API token is stored in GitHub. The workflow uses OIDC `id-token: write` and `pypa/gh-action-pypi-publish`. The PyPI project is created on successful first publication if the pending publisher is valid.

## C. Validate and publish deliberately

Open GitHub **Actions > Release validation and manual PyPI publication > Run workflow**. Select the default branch for the workflow and enter `v0.11.0` as its `tag` input.

The workflow:

1. Checks out the **existing** `v0.11.0` tag and rejects malformed tags, wrong version metadata and commits not on `main`.
2. Runs the detector-independent test suite and its required test-execution audit on Python 3.10 and 3.12.
3. Checks the Git source archive does not contain third-party JARs/classes/unlicensed manual, then builds **one** wheel and **one** sdist and runs `twine check`.
4. Installs the built wheel in a fresh environment **outside the checkout**, checks package metadata, CLI version, `doctor`, `import-circ`, and `report`.
5. Enters the protected `pypi` environment for an authorized reviewer to approve the actual PyPI upload.

**Do not approve the publication step if tests fail, an archive contains excluded assets, or the institutional/third-party distribution review remains unresolved.**

## D. Verify real user installation

Only **after** the PyPI upload succeeds:

```bash
python -m venv circyto-clean
source circyto-clean/bin/activate
python -m pip install --upgrade pip
python -m pip install "circyto[mudata]==0.11.0"
python -m pip check
circyto --version
circyto doctor
circyto import-circ --help
```

On Windows PowerShell, activate with `circyto-clean\Scripts\Activate.ps1` instead of `source`.

The `[mudata]` extra enables AnnData/MuData integration. Alignment and calling still require separately installed and permitted third-party tools; `pip install` cannot install CIRI3's Java JAR or BWA/STAR/SAMtools.

Before PyPI publication, an **available source-install alternative** is:

```bash
python -m pip install "circyto[mudata] @ git+https://github.com/liuifrec/circyto.git@v0.11.0"
```

This command works **only after the v0.11.0 tag exists** and Git is installed. For strict reproducibility, replace `v0.11.0` with the tag's immutable commit SHA. A source install is not proof of a published PyPI distribution.

## E. After successful publication

- Verify [PyPI circyto](https://pypi.org/project/circyto/) shows `0.11.0` and the wheel and sdist.
- Update README's provisional "not yet published" language with the verified PyPI URL, publication date, GitHub Release and optional installed-version badge.
- Record the release tag's commit and build/provenance evidence, without changing the November 20 submitted manuscript or inventing an article DOI.
- Keep separate verification records for historical manuscript figures and the evolving current software.

**The tag must remain immutable.** If further changes are needed after publication, issue a new version instead of moving or reusing `v0.11.0`.
