# CLI policy

This page documents the CLI conventions and “where do I put the detector/outdir?” rules that are easy to forget.

The core motivation: a user should not need to memorize Typer quirks or guess argument positions.

---

## Golden rules

1. Prefer `run-detector` for single-detector runs.
2. Always set an explicit output directory (`--outdir` or positional OUTDIR).
3. When in doubt, put paths early and run with `--help`.

---

## The “truth table”

### `run-detector` (single detector; canonical)

- Detector is positional after `run-detector`
- `--detector/-d` is accepted as an alias
- Output directory is a flag: `--outdir`

```bash
circyto run-detector <DETECTOR> \
  --manifest manifest.tsv \
  --outdir work/<run_name> \
  --ref-fa ref/genome.fa \
  --gtf ref/genes.gtf \
  --threads 8 \
  --parallel 4
```

### `run-batch` (single detector; compatibility alias)

- Detector is a flag: `--detector`
- Output directory is a flag: `--outdir`

```bash
circyto run-batch \
  --detector <DETECTOR> \
  --manifest manifest.tsv \
  --outdir work/<run_name> \
  --ref-fa ref/genome.fa \
  --gtf ref/genes.gtf \
  --threads 8 \
  --parallel 4
```

### `run-multidetector` (multiple detectors)

- Detectors are positional
- Output directory is a flag: `--outdir`

```bash
circyto run-multidetector \
  <DETECTOR_A> <DETECTOR_B> [<DETECTOR_C> ...] \
  --manifest manifest.tsv \
  --outdir work/<run_name> \
  --ref-fa ref/genome.fa \
  --gtf ref/genes.gtf \
  --threads 8 \
  --parallel 2
```

### `collect-matrix` (unified collector)

- Detector is a flag: `--detector`
- Input directory is a flag: `--indir`
- Output paths are explicit flags

```bash
circyto collect-matrix \
  --detector <DETECTOR> \
  --indir work/<run_name> \
  --matrix work/<run_name>_matrix/circ_counts.mtx \
  --circ-index work/<run_name>_matrix/circ_index.txt \
  --cell-index work/<run_name>_matrix/cell_index.txt
```

## `circyto detectors`

Typer’s autogenerated help does not naturally list “all detector choices” when detectors are implemented as pluggable units, so `circyto detectors` is the user-facing readiness table.

It prints:
- detector name
- readiness status
- detector type
- required external executables and bundled assets

This avoids the “read the README to find detector names” trap.

---

## `circyto doctor`

Many failures happen before circyto can do meaningful work, e.g.:

- `bowtie2` / `samtools` missing
- `bwa` missing
- `java` missing or too old
- `STAR` optional but required for STAR-based detectors

`circyto doctor` prints a report of what is found on PATH and what is missing.

Bundled asset resolution is intended to be cwd-independent; users should not need to `cd` into the repository root just to make `doctor` or `detectors` find the bundled CIRI-full assets.

For CIRI3:

- `READY` means circyto found a usable CIRI3 jar and Java, and the detected Java major version satisfies the bundled jar requirement (`>=12`).
- `NOT READY` means circyto could not find a usable CIRI3 jar or execution path.
- `PARTIAL` means local CIRI3 assets were found but the runtime contract is incomplete.
- Java `>=12` is mandatory for bundled direct CIRI3 execution; Java `17` is recommended.
- `samtools` is required for alignment handling.
- `bwa` is required for BWA mode.
- `STAR` is only required when STAR-based CIRI3 workflows are used.

## Detector semantics note

`ciri-full` is a single public detector name with two internal execution modes:

- paired-end rows use the upstream bundled CIRI-full Java Pipeline
- single-end rows use a bundled CIRI2-based fallback path

Both modes normalize to the same TSV schema, but the single-end path is **not** identical to upstream CIRI-full full-length reconstruction.

`ciri3` is a separate alignment-first detector and should be treated as a real backend rather than a scaffold. When `--command-template` is explicitly provided, that template is used for execution. Direct `java -jar` execution is used only when no template is provided and the local CIRI3 jar + Java contract is ready.

---

## Stability expectations

- Flags and core semantics should be stable across minor versions where possible.
- If a breaking change is required, it should:
  - be documented in `CHANGELOG.md`
  - be called out in `ROADMAP.md`
  - ship with a migration note in `docs/getting_started.md`
